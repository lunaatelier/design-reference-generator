Background

0. 추진 배경

기존 기획 MD와 디자인 산출물 간 연결 기준을 정리하고, 기본 운영 범위와 추가 인력 투입 가능 구간을 명확히 합니다.

계획 요약

기존 안은 6~12월 전체를 개발 기간으로 두었지만, 이미 기준이 정리된 상태라면 일정은 줄일 수 있습니다. 초기에는 핵심 항목을 순차 구축하고, 일정 압축이나 적용 범위 확대가 필요한 경우 추가 인력을 투입합니다.

1

일정은 단축하되 핵심 의존성을 관리한다

기준 설계에 1개월을 쓰지 않고 6월 안에 기준 정리와 Benchmark PoC를 함께 처리합니다. 핵심 자동화는 월별 기준으로 추진하되, 검수·정리·산출물 보완은 추가 인력 투입 시 병행 가능합니다.

2

제한 배포 후 확산 여부를 판단한다

초기 구축 단계에서는 12월 전사 완전 배포보다 11월 제한 배포, 12월 확산 판단이 현실적입니다. 적용 범위 확대, 산출물 검수, 교육 지원이 필요한 경우 추가 인력을 투입해 확산 준비를 병행할 수 있습니다.

3

디자이너의 Master Draft가 기준이다

V0 결과는 빠른 초안이고, Designer Master Draft는 품질 기준안입니다. Figma 자동화는 이 Draft를 DLS/DIS 기준으로 표준화합니다.

핵심 계획: 6~9월에 3대 자동화 항목을 순차 구축하고, 10월에 통합 QA와 v1.0 패키지를 완성합니다. 11~12월은 제한 배포와 전사 확산 판단 기간으로 운영합니다.

왜 3대 자동화 항목이 필요한가

자동화의 목적은 단순 속도 개선이 아니라, 기획 요구사항의 해석 편차, AI Draft 품질 편차, Figma/DLS 적용 불일치, 보안 리스크를 통제하는 것입니다.

①

Design Benchmark Automation

문제: 프로젝트마다 키워드, 레퍼런스, 무드보드, 디자인 방향을 반복적으로 수동 정리합니다.

필요성: 기획 MD에서 디자인 방향성을 자동 추출해 초기 해석 편차를 줄입니다.

성과: 리서치 시간 단축, 방향성 품질 균등화, 출처 관리 강화.

②

Vibe Coding Design Generation

문제: V0 등 AI 화면 생성은 빠르지만 요구사항 누락, 임의 기능 추가, 상태/예외 누락 가능성이 있습니다.

필요성: Planning MD와 ui_spec.json을 기준으로 화면 생성 프롬프트를 표준화해야 합니다.

성과: 빠른 화면 초안, 서브화면 파생, 제안/시연 Prototype 확보.

③

Figma Design System Automation

문제: 디자인 Draft가 좋아도 Figma 내부 구조, Token, Component, Layer가 정리되지 않으면 전달 품질이 떨어집니다.

필요성: Designer Master Draft를 기준으로 DLS/DIS 정합성을 자동 점검해야 합니다.

성과: 디자인 의도 보존, DLS 준수, 퍼블리싱 전달 품질 향상.

현실적 범위 재정의

초기 구축 단계에서는 모든 것을 자동화하지 않습니다. 12월까지는 “운영 가능한 최소 자동화 패키지”를 목표로 하되, 프로젝트 수·화면 수·검수 범위가 확대될 경우 추가 인력을 투입합니다.

12월까지 포함할 범위

  • 기획 MD 기반 디자인 키워드·벤치마킹·무드보드 생성
  • V0 기반 주요 화면 생성 프롬프트와 Prototype
  • Designer Master Draft 품질 기준 및 비교 리포트
  • Figma Token, Component, State, Layer Naming 기본 검증
  • 통합 QA 리포트, 보안 체크리스트, 제한 배포 가이드

전사 배포 이후 고도화할 범위

  • 전 프로젝트 유형별 도메인 룰팩
  • 완전 자동 Figma ↔ 구현 화면 동기화
  • 전사 자동 KPI 대시보드
  • 부서별 권한 관리 자동화
  • 다중 사용자 협업 워크플로우
범위 통제: 초기 실행 단계에서는 “전사 플랫폼 완성”이 아니라 “반복 가능한 운영 패키지 완성”을 목표로 합니다. 추가 인력은 화면 생성 보조, Figma 정리, QA 검수, 교육자료 보완 등 병행 가능한 영역에 우선 투입합니다.

Automation Process

2. 자동화 항목별 프로세스

각 자동화 항목의 입력, 처리, 검수, 보안 Gate, 산출물 흐름을 정리합니다.

상황별 인력 투입 실행 방식 관계도

월별 핵심 항목을 기준으로 단계 간 의존성을 관리하고, 각 단계의 산출물을 다음 달 입력값으로 넘깁니다. 일정 압축, 검수 범위 확대, 교육 지원이 필요한 경우 추가 인력을 투입해 병행 가능한 업무를 분리합니다.

보안 기준: 디자인 자동화 1.0

디자인 파일은 Figma, V0/Vibe Coding Prompt, DLS/DIS Token, Prototype, QA 리포트를 다루므로 Prompt·Figma·Token·QA 중심의 최소 보안 Gate를 적용합니다.

운영 결정: 디자인 자동화의 보안은 “기획 원문 보호”보다 Prompt 실데이터 금지, Figma 전체 공개 방지, 비승인 Token 저장 금지, QA 리포트 비식별화에 집중합니다.
필수 Gate

Prompt 보안

  • V0/Vibe Coding Prompt에는 고객명, 내부 URL, 실데이터, API Key를 입력하지 않습니다.
  • Sample, Dummy, Masked 데이터만 사용합니다.
  • 프롬프트 보안 위반 확정 건수는 0건이어야 합니다.
필수 Gate

Figma / Prototype 공유 권한

  • Figma 파일과 Prototype 링크의 전체 공개를 금지합니다.
  • 공유 권한은 프로젝트 담당자 중심으로 제한합니다.
  • 전체 공개 링크 발견 시 제한 배포를 보류합니다.
필수 Gate

Token / DLS 자산 보호

  • DLS/DIS Token은 승인 저장소에서만 관리합니다.
  • 개인 저장소, 외부 공개 저장소, 비승인 경로 저장을 금지합니다.
  • 비승인 Token 발견 건수는 0건이어야 합니다.
필수 Gate

QA 리포트 비식별화

  • QA 리포트에는 고객명, 내부 URL, 원문 캡처, 실제 운영 데이터를 남기지 않습니다.
  • Repository에는 오류 유형과 개선 룰만 저장합니다.
  • 비식별화율은 100%를 목표로 합니다.

디자인 자동화 1.0 보안 세부 반영

디자인 자동화는 현재 1.0 생성 단계이므로 기존 방식 대비 고도화 성과 비교는 제외합니다. 대신 V0/Vibe Coding, Figma, DLS/DIS, QA 리포트의 보안 기준을 실행계획 안에 포함합니다.

반영 원칙: 본 문서는 디자인 자동화 1.0의 실행계획을 유지하되, 외부 AI 입력·Figma 권한·DLS/DIS 저장소·QA 리포트 저장 기준을 보안 Gate로 추가한 전체 버전입니다.

V0 / Vibe Coding Prompt 보안

화면 생성 프롬프트에는 실제 고객 데이터, 내부 URL, 운영 화면 캡처, 고객사명을 포함하지 않습니다.

  • 프롬프트에는 Sample, Masked, Dummy 데이터만 사용
  • 내부 URL, IP, 계정명, 기관명, 실제 민원/거래/로그 데이터 입력 금지
  • 프롬프트 실행 전 민감정보 스캔 체크리스트 적용
  • 생성 결과에 실데이터가 재노출되지 않았는지 QA에서 확인

Figma 권한 및 Prototype 보안

Figma 파일과 Prototype 링크는 프로젝트 단위로 권한을 제한하고 전체 공개 링크 사용을 금지합니다.

  • Figma 파일 접근 권한은 담당자·검토자 중심으로 제한
  • Prototype 공유 시 외부 공개 링크 사용 금지
  • 캡처 이미지, 화면명, 테스트 데이터에 고객 식별 정보 포함 금지
  • 제한 배포 전 Figma 권한 점검 완료율 100% 확인

DLS/DIS Token 저장소 통제

Token, Variable, Component, State 정의는 승인된 저장소에서만 관리하고 개인 저장소 또는 외부 공개 저장소에 보관하지 않습니다.

  • Token / Component / Variable 소스 저장 위치 명확화
  • Style Dictionary, Tailwind, Figma Variable 산출물의 접근 권한 제한
  • DLS/DIS 원본과 자동 생성 파일의 Source of Truth 구분
  • 외부 납품 또는 공유 시 내부 Token 구조 노출 범위 검토

QA 리포트·Repository 비식별화

QA 리포트와 Knowledge Repository에는 원문, 고객명, 내부 정책, 실제 데이터가 아니라 오류 유형과 개선 룰만 저장합니다.

  • QA 리포트 저장 전 고객명·내부 URL·실데이터 제거
  • 오류 사례는 비식별화된 패턴과 개선 룰 중심으로 축적
  • Repository에는 화면 캡처 원본보다 문제 유형과 조치 방법 저장
  • 보안 위반 후보는 책임자 확정 전 배포 판단에 사용 금지

디자인 보안 Gate 흐름

1. 입력 데이터 확인 Prompt, Figma, Draft, QA 리포트의 민감정보 포함 여부 확인
→
2. 더미 데이터 치환 실제 값은 Sample / Masked 형태로 대체
→
3. 권한 제한 실행 Figma/Prototype/DLS 저장소 접근 권한 제한
→
4. 산출물 QA Prompt 로그, Token, Layer, Component, QA 리포트 검증
→
5. 보안 Gate 보안 위반 0건 확인 후 제한 배포

디자인 자동화 1.0 보안 강화 기준

디자인 파일은 기획 원문보다 Figma, Prompt, Token, Prototype, QA 리포트 보안이 핵심입니다. 따라서 디자인 보안은 “외부 입력 통제 + 디자인 자산 보호 + 공유 권한 제한” 중심으로 강화합니다.

보안 우선순위: 디자인 자동화에서는 V0/Vibe Coding Prompt에 실데이터가 들어가지 않도록 통제하고, Figma/Prototype 공유 권한과 DLS/DIS Token 저장소를 강하게 관리해야 합니다. 디자인 자산과 Token 구조는 회사 자산으로 취급합니다.
P0

Prompt 보안

V0/Vibe Coding Prompt에는 고객명, 내부 URL, 실제 운영 데이터, 계정 정보, API Key를 입력하지 않습니다.

  • Sample / Dummy / Masked 데이터만 사용
  • 프롬프트 보안 위반 확정 건수 0건
  • 위반 후보와 확정값 분리 기록
P1

Figma 권한 통제

Figma 파일과 Prototype 링크는 프로젝트 담당자 중심으로 제한하며 전체 공개 링크를 금지합니다.

  • Figma 권한 점검 완료율 100%
  • 전체 공개 / public link 0건
  • 외부 공유 시 만료일과 승인자 기록
P1

Token / DLS 자산 보호

DLS/DIS Token, Component, Variable, Layer 구조는 승인 저장소에서만 관리합니다.

  • 승인 Token 저장소 반영률 85% 이상
  • 비승인 저장소 Token 발견 건수 0건
  • 개인 저장소·외부 공개 저장소 사용 금지
P2

Prototype / 화면 캡처 보호

Prototype, 시연 링크, 화면 캡처에는 고객정보와 내부 업무 구조가 노출되지 않도록 관리합니다.

  • 이미지 내부 민감정보 Human 확인
  • 운영 화면 캡처 사용 금지 또는 마스킹
  • 제안용 이미지는 더미 데이터 기준으로 생성
P2

QA 리포트 비식별화

QA 리포트에는 고객명, 내부 URL, 실제 데이터, RFP 원문이 포함되지 않도록 합니다.

  • QA 리포트 비식별화율 100%
  • Repository에는 오류 유형·개선 룰만 저장
  • 원본 캡처 저장 시 사전 승인 필요
P3

제한 배포 통제

제한 배포 전 Prompt, Figma, Token, QA 리포트 보안 점검을 완료해야 합니다.

  • High Risk 미확인 0건
  • 보안 위반 확정 0건
  • 비승인 Token 0건
